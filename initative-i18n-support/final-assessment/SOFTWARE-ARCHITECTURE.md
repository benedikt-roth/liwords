# Software Architecture assessment

The architecture interest is to keep localization at presentation and integration boundaries, preserve the domain and consumer contracts, and make the contribution reviewable and reversible. The assessment is based on the checked-in architecture, initiative and code at `b5343a5e3`. Production topology, third-party subscriptions and historical records were outside the repository evidence. ## One authored catalog across builds

Use one version-controlled, repo-owned language catalog across all supported locales with sections inside the file. Keep application-owned help, legal, email and report wording in that source. Keep manual/section IDs, routes, accessibility semantics, links, markup and layout in their existing structural code. Review long prose in meaningful sections and allow only the rich-text slots the renderer can safely bind. Treat vendor-supplied UI library text, externally authored data, and existing persisted compatibility records according to their own source policies. Ask the requester to confirm the treatment of those records and permission to distribute build-derived projections. [Help requirements](../adr/0001-localized-help-and-stable-urls.md) · [Safe message rendering requirements](../feature-specification.md#catalogs-and-formatting) · [Docs ownership convention](../../liwords-ui/src/docs/registry.ts#L4)

| Option | Assessment |
| --- | --- |
| One authored catalog with local build projections | Preferred. Reuse a directly shared source where a build can read it. Produce deterministic read-only projections where package boundaries or native renderer resource shapes make that impractical. Keep the shared message subset small and use established libraries for message rules. Keep safe rich React elements and Go HTML template structures with their renderers. Validate IDs, completeness, argument types, plural rules, rich-text slots and artifact freshness, and measure the main and embed payloads. |
| Point every consumer directly at one checked-in file | Viable only with coordinated build inputs and a common supported resource format. A frontend catalog is excluded from the root Go production Docker context. A root or Go package catalog is outside the frontend Compose mount and the PDF Lambda package. Direct use can be an optimization for a compatible consumer, but it still produces packaged copies in separate executables/bundles. |
| Fetch a single hosted catalog from every deployed renderer | A single location for updates, at the cost of version skew, a new runtime dependency and startup/fallback complexity for the embed, early HTML and disconnected renderers. Defer this option unless the requester requires a single physical distributed file and accepts the changed availability model. |
| Independently maintained catalogs per runtime or locale | Fails the one-file authoring requirement and invites wording, parameter and plural drift. A shared ID list alone cannot provide message parity. |

A catalog-only diff must trigger all relevant verification. The current frontend filter matches `liwords-ui/**`, the backend filter lists separate paths, and the frontend CI build runs the main npm build. The standalone embed uses its own documented build and copy step. The PDF service deploys separately with `CodeUri: src/`. Go production Docker builds from the root with separate ignore rules. Choose a source location and packaging approach only after validating both Compose and native dev, the main and standalone builds, Go artifact embedding and the actual PDF packaging path. A build should work from a clean checkout without production data. Badge descriptions have a specific conflict with single-source authoring. Admins provide descriptions to `AddBadge`, the metadata RPC reads them from the database, and `cmd/gen-badges` now snapshots them into the app bundle to avoid a costly hot path. Catalog the shipped descriptions under stable badge codes, prove English parity and retain a documented fallback for dynamic or legacy metadata until maintainers decide how future badge definitions are created. Removing existing RPC data, changing descriptions at source, or restoring requests per rendered badge would change behavior. The maintainer needs to agree on a catalog-first workflow if the final single-file rule covers admin-supplied descriptions. ## Compatibility cases requiring design changes

1. **Browser rollout.** `GetSocketToken` returns the current frontend hash, while old app code offers a warning and still returns a connection URL. Its service worker intercepts sound files and handles notification clicks. Updating providers or changing the hash alone cannot guarantee that old tabs reload, particularly tabs in active games. Ship fallback-compatible reader and writer changes. Rehearse old client/new API, new client/old API, old/new socket and persisted readers, PWA, embed, reconnect and rollback. Decide with the owner when and how to prompt or require reload without interrupting matches or unsaved director work. Existing English fields and external contracts need an independent retirement decision if any removal is proposed. [Socket token](../../pkg/auth/authn_service.go#L226) · [Version check](../../liwords-ui/src/socket/socket.ts#L273) · [Service worker fetch rules](../../liwords-ui/public/sw.js#L130) · [Rollout ADR](../adr/0006-client-reload-and-api-compatibility.md)
2. **Historical challenge messages.** Both sender fields must be empty and the message must match a known server producer and context before mapping old text to a key. A missing user ID alone occurs in old records. Keep the raw English on ambiguity, including ambiguous returned tiles, and leave player-authored lookalikes as chat. The writer currently stores the system line in both game and spectator chats and sets `posted_to_chat` only when both stores succeed. The server omits the returned-tiles suffix when empty, while the current browser fallback for an invalid play includes it. Preserve each branch's English and verify reconnect, partial write, ordering and duplicate scenarios. Preserve tile strings and order from gameplay. [Challenge text and dual write](../../pkg/gameplay/game.go#L391) · [Browser challenge fallback](../../liwords-ui/src/store/store.tsx#L1076) · [Current chat sender classification](../../liwords-ui/src/chat/chat_entity.tsx#L106)
3. **Redis data and previews.** Upgrade reads before writing descriptors. Keep the legacy `username`, `message` and `userID` fields and their position for old readers. Add optional structured fields and read them defensively by field name in the new program. Retain the English legacy body on new rows for rollback and old clients. Keep historical rows untouched. Latest-channel Lua currently projects the raw body by position, and the Go preview trims it early. If a surface can contain system text, carry enough provenance and arguments to render first and then apply its display limit. The currently identified challenge writer posts only to game and spectator chats. Recent chat is indexed for PM, tournament and league channels. That matters when deciding where changes are needed. Preserve moderation filtering and channel discovery. [Redis write](../../pkg/stores/redis/add_chat.lua#L72) · [Redis history read](../../pkg/stores/redis/redis_chat.go#L209) · [Latest-channel Lua](../../pkg/stores/redis/latest_channels.lua#L24) · [Preview assembly](../../pkg/stores/redis/redis_chat.go#L329) · [Moderation filtering](../../pkg/mod/chat_review.go#L75)
4. **Account and formatting.** Attach locale to the active account and scope async reads and caches so a late response from the previous account cannot change the current language. Keep the default bundled and usable before lookup. A narrow private preference write is preferable to changing `UpdatePersonalInfo`, which updates several fields and requires a password when email changes. If the owner chooses a profile extension, use explicit presence to keep existing writers from clearing a preference. Keep language, timezone and game alphabet independent. Locale normalization in FR 12/AC 07 currently changes public broadcast dates and director time input conventions for some users, plus the birth-date control's order. Preserve existing formatting during the pilot and request an explicit release decision. 5. **Help routes and modal.** Keep the existing URLs and use the same locale-aware manual lookup for routes and the OBS help modal. It currently imports the streaming manual directly. The existing bare-manual redirect discards query/hash, so preserve working links and include meaningful query/hash in the acceptance cases for the proposed redirect behavior. ## Contribution gates

- Ask maintainers to review the proposed boundary and pilot before expanding extraction. Keep each PR small enough to compare English copy, affected contracts and domain behavior. Align provider changes with the Mantine migration, put changes to behavior-dependent manuals with the affected behavior, and regenerate checked-in outputs when changing protobufs or SQL. The root README documents npm/Rsbuild and regeneration. Run behavioral contract tests in addition to the `FILE` breaking checks configured in `api/buf.yaml`. [Repository README](../../README.md#protoc) · [Buf configuration](../../api/buf.yaml#L1) · [Manual convention](../../liwords-ui/src/docs/registry.ts#L4) · [Mantine migration plan](../../docs/mantine_migration_plan.md)
- Run catalog validation on an isolated checkout with local data, representative external fixtures, test recipients and controlled mixed versions. Exercise actionable messages and inputs, and intentionally test a missing key, bad argument and stale artifact. Maintain a small compatibility matrix for ports, URLs, RPC statuses, JSON fields, independently deployed consumers and scaled-down proxies such as the embed. Preserve exact English in the baseline and record reviewed corrections in the existing copy audit. The security policy limits account and data use in testing. ## Agreement after review

Engineering's isolated fixture supports the combination of direct Go embedding and derived browser/Python inputs from one source. The fixture exercised both main and single-bundle embed configurations with a minimal app, named arguments and plurals, controlled React content and opt-in Connect error details alongside current default text and status. The production app and Docker/SAM packaging still require a build proof. Product confirmed the practical effect of changing date and time inputs and identified the current badge authoring workflow and distinct challenge fallback wording. The architecture recommendation incorporates those as release gates. [Engineering assessment](SOFTWARE-ENGINEERING.md) · [Product assessment](PRODUCT-MANAGEMENT.md)

Architecture agrees with Software Engineering and Product Management to seek maintainer alignment, prove the one-source build path, start with a reversible unchanged-English pilot, and expand in reviewed slices. It favors existing component and protocol boundaries and explicit legacy fallbacks. Before wider changes, settle package/tooling ownership, affected consumers, private preference and reload policy, plus requester decisions on formatting parity and catalog scope.
