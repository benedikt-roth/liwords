## One language file and renderer feasibility

One version-controlled file can own all application-authored localized copy, including long-form help/legal text and message text for email, embeds, images and PDFs. Feature namespaces and locale sections can live in that file. A reasonable candidate is JSON under a small Go localization package, embedded directly by Go and projected only where a build or packaging boundary benefits. Translator-editable prose belongs in the source. Stable routes, section IDs, link destinations, email markup and render-time data remain owned by their existing application code. Runtime projections may contain materialized text, with machine provenance and no divergent editing, if the user accepts build-derived copies. [Central catalog ADR](ADR-0009-single-central-language-file.md) · [Existing renderer ADR](../adr/0002-message-contracts-and-catalog-runtimes.md)

Prefer the smallest common representation that works with established renderers. Explicit plural variants and named parameters map to each library's format. Keep plain shared messages on that subset. Rich UI entries can reference approved component slots, with no catalog-controlled attributes, URLs or arbitrary HTML. Apply contextual escaping via React or Go HTML templates. For long help/legal prose, evaluate Markdown with stable anchors and limited owned components. Compare multiline JSON strings against a legible single-file representation before pinning a format. Long-form reviewability, access to the actual help components and preservation of URL fragments are integration gates. A general template compiler, runtime catalog service, and system-wide localization interceptor would add complexity without evidence of need. [i18next plurals](https://www.i18next.com/translation-function/plurals) · [React Trans component](https://react.i18next.com/latest/trans-component) · [Go message rendering](https://github.com/nicksnyder/go-i18n) · [Help URLs](../adr/0001-localized-help-and-stable-urls.md)

| Option | Assessment |
| --- | --- |
| Direct physical file in all runtimes | Go can embed a package-relative file and JavaScript can import JSON. The repository still needs Compose and production path wiring, and the PDF deployment must package the file. Importing the complete file everywhere could include unrelated interfaces or large help content in the standalone embed and PDF artifact. Test this first where it costs little. |
| One authored file with deterministic projections | Preferred with user agreement. Keep namespace/form adaptation mechanical, use the standard renderer for plural selection and interpolation, and build projections as part of normal entry points. Check duplicate keys before ordinary decoding. Check key and named argument coverage, plural categories, rich slots, malformed-message fallback, exact English values and output reproducibility in CI. |
| Separate frontend, backend and content catalogs | Conflicts with the one-file requirement and introduces independent English and translation editing across shared messages. |
| One richer runtime format everywhere | Consider only if a tested format and mature libraries cover Go, JS and Python's real needs with lower maintenance than limited projections. Require proof of compatible rendering, build integration and safe rich copy. |
