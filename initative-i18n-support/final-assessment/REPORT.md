# Woogles internationalization initiative — final assessment

14 November 2026 · Reviewed checkout `b5343a5e3d2c9e93e2ec3e6f4cb319749f59b2dd`

## Executive summary

**Proceed with a maintainer-reviewed, English-parity pilot.** All three roles support the direction. Seek agreement on the contribution scope, prove the central catalog through the current build paths, and migrate a small set of messages with evidence from existing users' journeys and external client contracts. The initiative has enough design work to start that discussion. A full rollout requires explicit decisions on formatting, reloads, shared consumers and secondary build ownership. [Feature specification](../feature-specification.md) · [Role agreement](#review-process-and-agreement)

**Use one authored language file.** The proposed ADR uses one editable file across domains, renderers and future locales, with logical sections and build-derived resources where packaging requires them. One source is feasible at the tool level. Actual Woogles builds and deployment paths still need proof, and the requester should confirm that generated copies inside separate artifacts satisfy the requirement. [ADR 0009](ADR-0009-single-central-language-file.md) · [Engineering feasibility evidence](SOFTWARE-ENGINEERING.md)

**Resolve two conflicts with the non-breaking requirement.** A global switch to US formatting changes existing controls and display for some users, including birth-date field order and tournament director time inputs. Mandatory reloads can interrupt an active game or unsaved edit, and the current version check only offers a refresh. Preserve current behavior in the pilot and seek an explicit decision on how to reconcile both draft requirements before release. [Formatting conflict](#formatting-changes-existing-user-interactions) · [Mixed-version rollout](#mixed-versions-and-rollback)

## Findings and design implications

### Formatting changes existing user interactions

FR 12 and AC 07 bind date, time and number formatting to the selected UI language. Today registration derives birth-date field order from the browser, and the director time picker uses a browser-derived 12/24-hour preference. Some scorecard and broadcast timestamps also follow browser settings, while other views already use explicit US formats. Product reproduced the difference with `en-US` and `de-DE` at a fixed Europe/Berlin instant. The displayed date, hour cycle and separators differed even though the instant and timezone stayed fixed. Extract copy independently and preserve each touched call site's current format. Track any move to language-driven formatting as an explicit change with before/after acceptance examples. [FR 12–13 and AC 07](../feature-specification.md#catalogs-and-formatting) · [Registration date controls](../../liwords-ui/src/lobby/register.tsx#L55) · [Hour-cycle helper](../../liwords-ui/src/utils/datetime.ts#L10) · [Broadcast timestamp](../../liwords-ui/src/broadcasts/BroadcastsList.tsx#L16)

### Compatibility has to be proven at each boundary

The inventory contains 253 unique RPCs, matching the number of declarations in the checkout. It identifies 204 provisional UI-only methods, five shared methods, six external-only methods and 38 unresolved methods. Source references establish many known callers. They leave deployed scripts, clients and direct subscriptions to maintainer verification. The inventory covers RPC methods, while risk also sits in field meanings, socket frames, streams, exported files and app-owned rendering of external data. [API classification](../api-classification.md) · [Method inventory](../api-classification.csv) · [Export implementation](../../pkg/tournament/export.go)

- **UI-only candidates.** Prefer existing enum/status/count fields. Add an explicit semantic reason where wording currently triggers UI behavior, such as login verification or an expired verification token. Start with a small adapter on the verified endpoint. Keep legacy English/encoding available to old readers during the rollout. Test unknown reasons, missing parameters and the old server with the new UI. Replace text-based branching as each semantic path becomes available. [Login](../../liwords-ui/src/lobby/login.tsx) · [Verification](../../liwords-ui/src/lobby/verify_email.tsx) · [Analyze request](../../pkg/analysis/service.go#L540) · [Legacy error decoder](../../liwords-ui/src/utils/parse_woogles_error.ts)
- **Shared RPCs.** Preserve HTTP/Connect status, message fields, exact legacy English and successful payload shape for existing callers. Render the application-owned wording at the endpoint where parity is demonstrated. The shared `Register` method currently returns an empty success response, so use a representative validation error to test backend rendering. Add a semantic detail only on a verified compatible path. Binary protobuf compatibility alone gives insufficient evidence for JSON or strict callers. - **Excluded and unresolved consumers.** Keep existing default wire output for unknown consumers. Keep worker, OBS/SSE and NDJSON payloads, all machine-readable fields, and machine-targeted export formats stable. Review public projections explicitly when an IPC type is shared. The NDJSON path marshals selected game events directly as JSON. The OBS builder and preview, analysis result labels and director export controls are owned UI. - Keep semantic outcomes near their producer and render at the existing UI, service, job or report boundary. Apply English fallbacks at display time and keep technical diagnostics in their existing logging paths. A localized message must never determine game state, authorization, session state or retry behavior. Keep the socket relay and shared event bus independent of user locale. ### Challenge chat requires read-path compatibility before new writes

Challenge results feed player and observer channels. Redis history reads fields positionally, and recent-channel previews pull original text with Lua and can trim before display. There is also a client fallback when the normal chat post fails. Some existing fallback wording differs from persisted wording, so compare each branch against its baseline. Upgrade readers first and preserve the English body for old readers and rollback if a structured descriptor is written. Preserve old records. Recognize known historical lines using channel and system-origin evidence with an exact, validated format. Display the original text for unknown forms or malformed data. Test sender lookalikes, partial writes, live delivery, reconnect/history, current preview behavior, expiry, deletion and moderation's senderless-line exclusion. Verify each affected Redis reader rather than assuming every channel uses the same preview path. [Challenge producer](../../pkg/gameplay/game.go#L406) · [Redis chat store](../../pkg/stores/redis/redis_chat.go#L209) · [Moderation discovery](../../pkg/mod/chat_review.go#L83) · [Historical messages ADR](../adr/0007-historical-system-message-rendering.md)

### Account locale is private and the selector is a separate decision

A narrow authenticated locale preference prevents unrelated profile updates by old clients from overwriting it. Resolve to `en-US` for guests, for absent or invalid values and on logout. Tie preference reads and in-flight responses to the active account, including cache invalidation at account switch. Check session privacy and cross-device reads independently of the eventual tester role or flag. Keep the existing Secret features local storage behavior separate from the account preference. For email, resolve the recipient's context without a live browser. Preserve transport, links, time context, recipient selection and timing. [Private profile methods](../../pkg/profile/profile.go#L188) · [Current Secret features](../../liwords-ui/src/settings/secret.tsx) · [Selector ADR](../adr/0005-experimental-language-selector-access.md) · [League email paths](../../pkg/league/league_notify.go)

### Secondary entry points and content determine whether one file is practical

The application shell and standalone embed have different entry points, and Go produces the initial cached embed HTML. A React provider alone cannot cover early HTML, Lua-/WASM-derived errors, CSS and canvas captions, speech, notification callbacks, email or PDF generation. Build resources into the bundle or job that owns each output. Preserve IDs, expected markup, links and behavior. Stay with existing help routes initially. Point the in-app help modal and document page to the same localized content resolver. The bare-manual redirect currently constructs a path without search or hash. Record that baseline and handle any deliberate fix explicitly under the help compatibility decision. Treat legally reviewed copy as intact prose and preserve accepted rendering. [Go embed](../../pkg/embed/service.go#L98) · [Embed build](../../liwords-ui/rsbuild.embed.config.ts) · [Manual route](../../liwords-ui/src/docs/DocPage.tsx) · [OBS help modal](../../liwords-ui/src/broadcasts/OBSHelp.tsx) · [Terms of service](../../liwords-ui/src/about/termsOfService.tsx) · [Secondary renderer ADR](../adr/0004-secondary-renderers-and-email.md)

The most consequential packaging risk is a catalog-only edit that bypasses a relevant build. The frontend workflow filters on `liwords-ui/**`, local Compose sees a frontend-only bind mount, and the API Docker context excludes the UI. The embed has a documented standalone build and copy step. Go emits a public-cacheable page referencing an unhashed JS URL, so older HTML and newer JS can meet independently. The PDF service is separately and manually deployed with SAM. Verify input visibility and the built resources in each path, and identify who publishes the production embed. Prove same-source generation, startup, bundle size and stale-output detection in a clean checkout. Include independent HTML/JS and API/PDF versions in the compatibility checks. [Workflow filters](../../.github/workflows/build-and-deploy.yml#L61) · [Compose frontend](../../docker-compose.yml#L242) · [Docker context](../../.dockerignore) · [Embed HTML and cache](../../pkg/embed/service.go#L157) · [Embed build instructions](../../liwords-ui/src/embed/README.md) · [PDF deployment](../../services/tourneypdf/README.md)

The rich-text test found that a catalog entry could override the code-supplied link when using the candidate React renderer. Keep link targets and component props in code. Require the validator to reject slot attributes and unauthorized markup, and test both link integrity and untrusted interpolation. [Engineering experiment](SOFTWARE-ENGINEERING.md#isolated-proof-run) · [React Trans component props](https://react.i18next.com/latest/trans-component#overriding-react-component-props-v1150)

Badge descriptions present a separate authoring dependency. Staff supply descriptions through an API, and the build ships a generated database snapshot for fast player display. Use stable badge codes for catalog lookups. Preserve the metadata API and existing English during the transition. A final catalog-first badge workflow needs agreement from the people who add badges and maintain the current build. ### Mixed versions and rollback

Keep the server and new UI able to read today's contracts. Deploy compatible readers before emitting optional data or writing new record versions. Preserve legacy English and gate any changed representation on a verified capability or separate versioned path. Rehearse old/new combinations in both directions across API, socket, web and separate embed. Also test already-connected tabs, pending and unsent inputs, reconnect, embedded and installed PWA launches, independent RPC calls, and rollback after a structured chat write. The existing socket hash check shows an optional notice on token fetch and then connects. A new bundle cannot change an already-running old bundle's behavior by itself. Decide how mandatory reload fits with continuity. If maintainers require enforcement, agree on a preparatory release, a safe transition away from active play/editing, and recovery from cache or deploy mismatch. ## Decisions to answer or delegate

| When | Decision owner | Question and working recommendation |
| --- | --- | --- |
| Before catalog implementation | Requester | Does one file permit build-derived copies and subsets inside independently distributed artifacts? Should future locales, migrated long-form legal/help and future badge descriptions all share that source? The ADR assumes one authored file total and derived packaging. |
| Before formatting changes | Requester with maintainers | Should existing regional formatting take priority over FR 12/AC 07 in the English release, or is changed display and input order acceptable on named screens? Preserve behavior while open. |
| Before rollout changes | Requester with release maintainers | Is a mandatory reload an approved exception to parity? If so, which active games, pending commands and unsaved editor states must be allowed to finish, and how are pre-existing tabs, embeds, PWAs and rollback handled? Keep compatibility throughout the pilot. |
| Before each changed public boundary | API and integration maintainers | Which clients and subscriptions use the candidate RPCs, socket frames, event feeds or exports, and do any treat strings, shapes or artifact bytes as a contract? Which endpoints can safely emit structured metadata and under what capability? Preserve existing default contracts where evidence is incomplete. |
| Before committing to the runtime | Frontend, Go and report maintainers | Which small set of runtime/template features and build packaging can the team support, and who owns shared catalog changes, independent embed/PDF shipping and reproducibility checks? Decide after the actual-build proof. |
| Before selector and persistence work | Identity/product maintainer | Should testers reveal the selector through the proposed role or a developer flag? Which narrow authenticated preference API and write semantics will coexist with previous clients? Define authorized visibility independently of account storage. |
| Before structured system-chat writes | Gameplay, storage and moderation maintainers | Which historical forms are actually deployed and which readers must survive rollback? Approve fixtures, origin rules and retention/preview behavior before enabling new writes. |
| Before help, badge and output migration | Docs, admin and report maintainers | Which language should future explicit/unprefixed help URLs choose? Should bare-manual query/fragment handling be fixed in its own patch? Can badge authoring move from the current DB workflow to the catalog? Which report labels are presentation versus consumed formats, and which existing server timezones must persist? |
| Before adding a community language | Maintainers | Who reviews translations and legal copy, which completeness and accessibility checks gate locale enablement, and how do external consumers explicitly opt in? Keep production `en-US` until those choices are agreed. |

## Evidence and limits

This assessment traces the reviewed checkout and draft to representative source paths, cross-checks the RPC inventory and uses isolated feasibility experiments. The engineering fixture and the regional-formatting reproduction validate specific seams. They leave full Woogles application tests, browser/Redis integration, final package/deploy behavior and the complete deployed consumer inventory for implementation review. The repository's domain boundaries are code-derived and remain open to maintainer validation. The assessment records recommendations and stakeholder constraints for review.
